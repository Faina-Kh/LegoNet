# Reproducing LegoNet experiments

This document defines the experiment scope and scientific claims for the
public reproduction workflow. The workflow is being implemented incrementally;
the commands and machine-readable reference files will be added after the
experiment inventory is fixed.

## Verification levels

LegoNet will provide two distinct verification levels:

1. **CPU smoke reproduction** checks installation, configuration, fixture-data
   parsing, evaluation bookkeeping, and structured result generation. It does
   not reproduce a paper metric.
2. **Scientific reproduction** runs inference with a documented research
   checkpoint on the corresponding public dataset split and compares the
   result with a verified current-code reference. Where a matching paper value
   exists, it is shown separately for scientific comparison.

Future runs will be checked against the verified current-code reference, not
against rounded values transcribed from a paper.

## Roots estimation scopes

The roots experiments contain two different ways to obtain image-level trait
estimates. They must not be combined into a single result category.

### Direct per-image estimation

The direct models take a complete image as input and estimate total root length
(TRL) directly. The available direct-estimation checkpoints cover TRL only:

| Experiment | Network type | Estimate type | Released target |
|---|---|---|---|
| Direct TRL, keypoints | `per_image_estimation` | `keypoints` | TRL |
| Direct TRL, regression | `per_image_estimation` | `regression` | TRL |

Verified Test-set results:

| Configuration | Source | Mean relative difference | 1-FVU |
|---|---|---:|---:|
| Keypoints | Paper | 16.0% | 0.92 |
| Keypoints | Current code | 14.40% | 0.93 |
| Regression | Paper | 13.70% | 0.92 |
| Regression | Current code | 16.70% | 0.935 |

These values describe direct TRL inference and are not derived by aggregating
per-root predictions.

### Per-root estimation and image aggregation

Per-root models first detect roots and estimate traits for matched individual
roots. Their image-level metrics are calculated afterward from the per-root
outputs:

- image TRL is the sum of per-root length estimates;
- image mean diameter is the mean of per-root diameter estimates; and
- image white fraction is the mean of binary per-root color estimates.

Consequently, the image-level rows in the per-object regression, standalone
keypoint, and multibranch tables are **per-root estimation aggregation**
results. They are not direct per-image model results.

The standalone keypoint per-root Test result has no corresponding paper Test
value. It is retained as a verified checkpoint benchmark and documented
negative result: its color output collapses to the white class. The paper
instead reports the multibranch model as the effective keypoint-based per-root
alternative. Appendix results for the standalone configuration use the
Validation split and form a separate experiment.

The standalone keypoint Test result includes a mean-diameter relative error of
20.6% and a mean-diameter absolute difference of `0.076`. The absolute
difference is not a percentage.

## Experiment identity and split policy

Every reproducible run will have a stable identifier that includes its
evaluation split. Planned roots identifiers include:

```text
roots-direct-trl-kp-test-v1
roots-direct-trl-reg-test-v1
roots-per-object-reg-test-v1
roots-per-object-kp-test-v1
roots-per-object-kp-val-appendix-v1
roots-per-object-multibranch-test-v1
```

A Test result must never be compared with a paper value reported only for the
Validation split. Each manifest will also identify the training-data variant
(`all_data`, `limit_5`, or mixed branch pretraining) and checkpoint provenance.

## Result presentation and images

Reference metrics should be stored as structured data and rendered as Markdown
tables. Spreadsheet screenshots should not be used as the authoritative result
record because they are difficult to review, search, update, and consume with
assistive technology.

Visual examples are useful when they explain model behavior. Prefer images
regenerated by the released code from the documented checkpoint and public
dataset. A small number of representative examples may appear in a dataset or
reproduction README, with a larger optional gallery under `docs/`.

If a figure is copied directly from a published paper rather than regenerated,
its caption must identify the source and the repository must have permission
to redistribute it under the figure's applicable license. A paper citation by
itself does not necessarily grant image redistribution rights.

Examples include:

- direct per-image keypoint maps with the predicted and ground-truth TRL;
- matched root boxes with length, diameter, and color predictions;
- a multibranch example that illustrates successful color estimation; and
- a standalone keypoint example that illustrates the all-white color collapse.

Examples should be selected by a documented rule, such as fixed image IDs,
rather than chosen only because they look favorable.

## Implementation sequence

1. Fix the experiment inventory, split scope, scientific claims, and metric
   terminology in this document.
2. Define versioned machine-readable manifests for each verified experiment,
   including dataset, checkpoint, configuration, training-data provenance,
   environment, and random-seed policy.
3. Export evaluation results to a stable JSON schema with metric denominators
   and evaluated image/object counts.
4. Store verified current-code references and paper-comparison values
   separately, with explicit per-metric tolerances.
5. Add dataset and checkpoint checksum validation.
6. Add a thin reproduction runner that resolves a manifest, invokes the
   existing inference path, records provenance, and compares results.
7. Add the deterministic CPU smoke fixture and run it in CI.
8. Run each scientific manifest in the documented GPU environment and archive
   the resulting logs, environment record, metrics, and comparison report.
9. Publish verified checkpoints in a versioned archive and add permanent URLs
   and checksums to the manifests.
10. Add regenerated visual examples after the numerical reproduction path is
    verified.
